# Add block-level patch assets to ZIP releases

The full ZIP is 167 MB and the Electron executable alone compresses to 109 MB, 65% of the archive. electron-builder rewrites its version resource and asar integrity data on every build, so the executable always changes and a file-level delta is at least that large. Users should not re-download the runtime to receive a small change.

CI now publishes up to three block patch assets per release, one for each recent published baseline. A patch asset is a ZIP containing `patch.json` (base manifest hash, per-file size and SHA-256, and either a block recipe or a full-file reference), `literals.bin`, the target `update-manifest.json`, and full copies of files that cannot be patched. Target files are split with gear-hash content-defined chunking (4-128 KiB, 32 KiB target); the recipe copies matching base chunks and appends literal runs. Only files of at least 512 KiB whose base bytes are owned by the base manifest are patched, which in practice means the executable and `app.asar`, so recipes and literal streams stay small.

The updater tries the patch matching its installed manifest hash first, then the legacy file-level delta, then the full ZIP. Each asset is validated through the embedded manifest, file sizes and SHA-256, and any failure falls back without user input. Staged files are ordinary files, so the Windows apply helper, backup and rollback behavior are unchanged. Publishing patches for the previous three releases keeps every asset set within roughly one release of storage per version, and older releases remain installable from their full ZIP. During the transition one release also keeps a legacy delta so existing 0.1.20 installs upgrade without a full download. This supersedes ADR 0002's rejection of binary patching, not its release format.
